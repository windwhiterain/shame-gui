# API consistency audit: tests & examples

Audited every `.rs` under `crates/shame-gui/tests/` and `crates/shame-gui/examples/`
against the core API surface (`app.rs`, `graph/`, `gui/`, `material.rs`, `port.rs`).

## Summary

| Severity | Count | Headline |
|----------|-------|----------|
| Critical | 1 | `text_scene_with` creates + discards an internal TextSystem |
| High | 3 | Dual DAG-node API, pusH_constant example is degenerate, snapshot font non-determinism |
| Medium | 3 | `WidgetNode::new_default` dead code, `IdGroup` needs `empty()`, unused `extend` |
| Low | 3 | Import style inconsistency, `make_ib` manual loop, duplicated instance structs |

---

## 1. Critical

### 1.1 `text_scene_with` allocates a TextSystem it throws away

`tests/common/scenes.rs:366-369`
```rust
pub fn text_scene_with(text_system: TextSystem) -> (App, TextSystem) {
    let (app, _) = text_scene();  // creates TextSystem::new() internally, binds _, drops it
    (app, text_system)
}
```
- `text_scene()` internally calls `TextSystem::new()` and bundles the result into its
  return tuple. `text_scene_with()` calls `text_scene()`, immediately drops the inner
  TextSystem, then returns the caller-supplied one.
- Callers that want to inject a deterministic font already know they must throw away the
  internal allocation — this is wasteful and confusing for new readers.
- **Fix**: `text_scene()` should just build the `App` (no TextSystem creation). Split into
  `text_scene_app() -> App` and have callers supply their own TextSystem. Kill
  `text_scene_with`.

## 2. High

### 2.1 Two competing DAG-node input/output APIs

`GraphBuilder::add_node` accepts `inputs: impl PortGroup` / `outputs: impl PortGroup`.
Both `IdGroup { ids: Vec<PortId> }` and tuples of `Port<T>` implement `PortGroup`,
so callers can choose either style:

**Tuple style** (calc.rs, viewport_rect_scene):
```rust
b.add_node(eval, (ports.operand1, ports.vec_a), (ports.sum, ports.dot));
```

**IdGroup style** (rects_scene, blend_scene, text_scene):
```rust
b.add_node(eval, IdGroup { ids: vec![] }, IdGroup { ids: vec![fill_id] });
```

- Tuple style is ergonomic but maxes out at 4 elements (the highest N-tuple `PortGroup` impl).
- IdGroup style is required for empty inputs (source nodes that always run) and for >4 ports.
- The two styles appear side-by-side in `viewport_rect_scene` — the tuple version is used
  for the DAG node `(vp_ports, fb_port)`, then immediately after, `IdGroup`-based
  nodes are auto-generated by `register_render_object`.
- **Fix**: Pick one style as canonical for user-facing docs/examples. If tuples are the
  default, add a `pub fn empty() -> IdGroup` or `impl Default for IdGroup` so
  `IdGroup::empty()` replaces the noisy `IdGroup { ids: vec![] }`. If IdGroup stays,
  deprecate tuples (or keep them as a private convenience and stop using them in examples).

### 2.2 `push_constant.rs` example has zero user-defined DAG nodes

`examples/push_constant.rs` never calls `app.graph_builder()` — it calls
`register_render_object` three times and then `finalize_graph()`. The graph topology is
entirely auto-generated (upload + bind-group nodes per registration).

- The example is advertised as a "Push constant demo" but it doesn't demonstrate how to
  wire a push-constant port through a custom DAG node (the common pattern for live values).
- All three registrations share the same `fb_size: Vec2u::new(0, 0)` initial value and use
  `HAS_FB_PUSH_CONSTANT: true` — the Canvas overwrites fb_size each frame via the built-in
  injection, so the initial value is irrelevant. This is non-obvious.
- **Fix**: Add at least one DAG node that writes a dynamic value into a push-constant port,
  or rename the example to `static_render_object` and create a separate example showing
  the push-constant + DAG-wire pattern (like `viewport_rect_scene`).

### 2.3 Snapshot tests mix deterministic and non-deterministic text

| Test file | Text system used |
|-----------|-----------------|
| `snapshot_viewport_rect.rs` | `test_text_system()` (embedded Inter font) |
| `snapshot_text.rs` | `test_text_system()` |
| `snapshot_push_constant.rs` | `test_text_system()` |
| `snapshot_form.rs` | `test_text_system()` |
| `snapshot_rects.rs` | `TextSystem::new()` (system fonts) |
| `snapshot_blend.rs` | `TextSystem::new()` (system fonts) |

`TextSystem::new()` loads system fonts, which vary across OS and machine — glyph metrics,
line heights, and fallback behavior can differ between Windows, macOS, and Linux.

- `snapshot_rects` and `snapshot_blend` don't actually render text, so the TextSystem
  value is irrelevant for pixel output. But it's still a latent bug: if someone adds
  a label to the rects scene, the golden will break on different machines.
- **Fix**: Use `test_text_system()` uniformly. The `TextSystem::new()` calls should be
  replaced with `common::test_text_system()`.

## 3. Medium

### 3.1 `WidgetNode::new_default` is dead code

`gui/widget.rs:213-218` defines `WidgetNode::new_default(port)` as a convenience over
`WidgetNode::new(port, Data::default())`, but no test or example uses it. Every call site
writes `WidgetNode::new(port, NumberWidgetData::default())` manually.

- **Fix**: Either convert callers to use `new_default` or remove it.

### 3.2 No `IdGroup::empty()` / `Default for IdGroup`

The `rects_scene`, `blend_scene`, and `text_scene` all write:
```rust
IdGroup { ids: vec![] }
```
for source nodes (empty inputs = always run). This allocates `Vec` just to hold zero elements.

- **Fix**: `impl Default for IdGroup { fn default() -> Self { Self { ids: vec![] } } }`
  so callers can write `IdGroup::default()` or `IdGroup::empty()`.

### 3.3 `InstanceBuffer::extend` is unused

`material.rs:137-141` defines `pub fn extend(&mut self, instances: &[I])` but every
consumer uses a manual `for` loop calling `push()`:

```rust
// push_constant.rs:114-123
for &(x, y, ref color) in colors {
    ib.push(&RectInstance { ... });
}
```

- **Fix**: Either remove `extend` or demonstrate it in at least one example/test
  (e.g. `ib.extend(&instances)` where `instances` is collected into a `Vec` first).

## 4. Low

### 4.1 Inconsistent `Vec2u` import style within `widget.rs`

`tests/widget.rs` uses full-path `shame_gui::math::Vec2u::new(800, 600)` on lines 26,
195, 217 while all other types (`Vec2`, `Rect`, `Port`, etc.) are imported at the top
with `use`. Other test files (`rect.rs`) import `Vec2u` at the top.

- **Fix**: Add `use shame_gui::math::Vec2u;` to widget.rs.

### 4.2 `make_ib` in push_constant example manually loops

`examples/push_constant.rs:114-123` iterates `&[(f32, f32, Color)]` and calls `push`.
This is a closure-captured helper that duplicates what `extend` could do.

- Not a bug, just another `extend`-should-exist-then-use-it data point.

### 4.3 Duplicated instance structs in `scenes.rs`

`GradientRectInstance` and `TransparentRectInstance` (`scenes.rs:34-40` and `99-105`)
have identical field layouts:
```rust
pub rect: Rect,
pub color_a: Vec4,
pub color_b: Vec4,
pub z: f32,
```
The only difference is which material they're associated with. Since these are
`GpuStruct` types bound by material type, Rust's type system prevents sharing one
struct between two materials. However, a common `pub struct GradientRectData { ... }`
with `type Instance = GradientRectData` on both materials would work because the
instance type is a compile-time parameter, not a value. The duplication isn't
harmful today but would be a maintenance liability if more gradient materials are
added.

## 5. No-issue confirmations (audited and clean)

- Arena / graph-builder / finalize ordering is correct everywhere (calc.rs follows the
  three-phase pattern from AGENTS.md).
- `build_state_ports` usage is consistent between calc.rs and its documentation.
- `Color::to_linear()` is called at the right point in every instance construction
  (no drift into GPU-side sRGB).
- The `dirty` → `graph.mark_dirty` → `graph.tick` → `canvas.clear_dirty` pipeline is
  honored in `app.rs` and `static` readback in `scenes.rs` snapshots.
- `Vec2` / `Vec2u` / `Rect` all use physical-pixel, y-down coordinates uniformly.
- Widget handle types (`Port<T>`, composite ports) are properly `Clone + Copy` and
  not accidentally re-allocated.
